S2P Data Model Foundation
What & Why
Add the data fields, history table, and config plumbing needed to support canonical Source-to-Pay (S2P) vocabulary, savings-type tagging, baseline tracking, and per-gate Delegation of Authority (DOA) SLA tracking. Nothing in the dashboard restructure can be built correctly until the data has the right shape.
This is foundation only. No UI changes in this ticket. The dashboard rebuild that consumes this schema is a separate set of tickets that follow once the data model lands.

New table: opportunity_stage_history
A row is written on every stage transition. This table cannot be reconstructed retroactively — every transition from this point forward must be captured.
sqlopportunity_stage_history (
  id                       uuid PRIMARY KEY,
  opportunity_id           uuid NOT NULL REFERENCES opportunities(id),
  from_stage               text,                   -- nullable for initial backfill row
  to_stage                 text NOT NULL,
  transitioned_at          timestamp NOT NULL,
  transitioned_by_user_id  uuid REFERENCES users(id),  -- nullable for backfill / system transitions
  transition_reason        text,
  notes                    text
)

Computed-at-query-time fields
These are NOT stored; they are computed by a helper function and included in every API response that returns opportunity records:

time_in_current_stage — hours since stage_entered_at
breaching_sla — boolean, computed by gate_sla_breach(opportunity) which reads the current stage and the corresponding SLA from GATE_SLAS

Backfill mapping (embedded for pre-write review)
sql-- Source: existing platform_status field on opportunities table
-- Target: new canonical_stage, savings_type, savings_classification fields
-- All backfilled records receive classification_needs_review = true

platform_status='Proposed'                → canonical_stage='Identified',          savings_type='Identified'
platform_status='Approved'                → canonical_stage='Awarded',             savings_type='Negotiated'
platform_status='Executing'               → canonical_stage='In Implementation',   savings_type='Implemented'
platform_status='Realized'                → canonical_stage='Realized',            savings_type='Realized'
platform_status='Rejected'                → canonical_stage='Closed-No Action',    savings_type='Identified'
platform_status='Rejected (under review)' → canonical_stage='Under Re-evaluation', savings_type='Identified'

-- ALL backfilled records also receive:
savings_classification      = 'Hard'
classification_needs_review = true
baseline_method             = 'Internal Estimate'
baseline_value              = NULL
baseline_source             = 'BACKFILL — needs review'
sourcing_strategy           = 'Unclassified'
stage_entered_at            = COALESCE(updated_at, created_at)

-- For each backfilled opportunity, write ONE row to opportunity_stage_history:
INSERT INTO opportunity_stage_history (opportunity_id, from_stage, to_stage, transitioned_at, transition_reason)
VALUES (<id>, NULL, <canonical_stage>, <stage_entered_at>, 'BACKFILL');
Note on Closed-No Action and Under Re-evaluation backfill: these records are tagged savings_type='Identified' because the prior stage cannot be reconstructed without history that doesn't yet exist. Going forward, opportunity_stage_history will record the actual prior stage on every transition.

Rollback plan
If the migration causes downstream failures:

Run the down migration — drops all ten new columns and the opportunity_stage_history table.
Restore previous OpenAPI spec from git; re-run codegen.
Backfill data is non-destructive (additive UPDATE only on existing records, no source data deleted), so no source data is lost on rollback.
The platform_status field is untouched throughout this migration and remains the fallback truth for stage information.

Why this matters (for the reviewer)
Two things in this ticket cannot be added cheaply later:

The stage history table. Cycle-time analytics, audit trails, and funnel reconstruction all depend on having a row per transition. If we don't capture this from day one, every transition until we add it is lost forever.
Baseline fields paired with savings types. The first question a CFO asks about a "$8.3M realized" number is "saved against what?" Without baseline_method, baseline_value, and baseline_source, that question has no answer.

Everything else in this ticket can be retrofitted. These two cannot.
