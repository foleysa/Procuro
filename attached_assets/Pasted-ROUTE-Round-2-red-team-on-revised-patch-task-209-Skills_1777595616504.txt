MEDIUM — items worth pre-ship attention
RT-91. The render-time scrubber is load-bearing but its false-positive risk isn't addressed.
Step 1 says the scrubber strips "SQL keywords (select|from|where|group by|join|insert|update|delete), dollar-prefixed param markers ($1, $2, …), params: blobs, file paths, and stack-frame markers from any string that ends up on the screen."
Two failure modes:

False positives. A legitimate alert title containing the word "select" (e.g., "Vendor selected for sole-source review" or an opportunity description like "Update from Q3") would get scrubbed. The scrubber would silently mangle real user-facing content.
Regex coverage gaps. The pattern list is a denylist. Tomorrow a new error format introduces "ERROR at line 47:" or "/usr/local/lib/..." — neither matches the listed patterns. The scrubber catches today's known leaks and silently fails on tomorrow's.

Severity: medium. The scrubber works for the alerts SQL leak shown in the screenshot, but as a long-term contract it has known weaknesses that the spec doesn't acknowledge.
Fix: add to step 1 — "The scrubber operates at the error-message rendering boundary, not on all rendered text. It scrubs strings flowing into error/failure-state UI components specifically; legitimate card content (alert titles, opportunity descriptions) bypasses the scrubber. The pattern denylist is intentionally narrow for the known leak surface; broader allowlisting (only render error messages from a known-safe template registry) is the correct long-term contract but out of scope for this patch."
This makes the scrubber's scope explicit and acknowledges it's a tactical fix, not a structural one.
RT-92. The hand-off contract with #204 has three dimensions but misses load-order timing.
Constraint says #204/#209 don't collide on DOM, aggregator response shape, or data sources. Good. But:

If both are loaded simultaneously, what's the visual hierarchy? Spec says "if #204 ships first, #209 layers... If #209 ships first, the four enriched cards reserve nothing." But what if both ship in the same release? Or both are in active development and a user gets a partial deploy?
If the aggregator endpoint is shared (GET /api/today/feed) and both tasks add to its response, what's the version contract? Does the response payload's TodayFeedItem.kind set get bumped, or are #209's enrichments added to existing kinds and #204 adds new kinds, with neither needing a version bump?

The spec says "#204 owns any new kinds and any new substrate-derived fields" which implies the version contract: existing kinds get extended (additive, non-breaking), new kinds get added (additive, non-breaking). Both tasks can ship independently.
But the load-order question — what does the page render during a deploy where one has shipped and the other hasn't — isn't addressed.
Severity: medium. Both tasks will probably handle this with feature flags or capability detection in practice, but the spec doesn't name the responsibility.
Fix: add to constraints — "Load-order resilience: the page renders correctly with any combination of (#209-only, #204-only, both, neither). Each task's enrichments are independently feature-gated by capability detection on the aggregator response (#209 enrichments rendered when the existing TodayFeedItem.kind payloads include the new fields; #204's new section rendered when the response includes its new kinds). The Today page does not assume both tasks have shipped."
RT-93. The RT-83 structural-backlog verification step ("real working backlog or counting artifact") doesn't have criteria.
This is the recursive forced-choices-need-criteria pattern again. Step 5 says: "Before shipping, the executor verifies whether the current 3,822 pending-approvals figure represents a real working backlog or a counting artifact (stale rows, never-pruned status, missed cleanup). The verification result is named in the implementation summary."
But what's the verification method? Sampling 100 rows and inspecting their dates? Querying for never-acknowledged opportunities older than X? Asking an operator? "Verifies" is undefined.
Severity: medium. The executor will pick a method, and the result is binary (real or artifact), but the method affects the answer.
Fix: add to step 5 — "Verification method: query for the age distribution of pending approvals (oldest 10, median, newest 10), the per-lever breakdown, and the count of approvals with no activity in 30+ days. If 30+-day-stale approvals are >50% of the total AND the per-lever breakdown shows concentration in a single lever (suggesting a producer side bug rather than legitimate backlog), classify as artifact. Otherwise classify as real working backlog. Include the verification query results in the implementation summary."
This makes the verification reproducible and the classification boundary explicit.
