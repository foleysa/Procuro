MEDIUM — issues that warrant pre-ship attention
RT-76. The substrate-output enumeration has the same forced-choice-without-criteria pattern that step 3 and step 6 had — applied to five new choices.
Step 1 says: "Substrate-output enumeration (mandatory): the audit must additionally enumerate the funnel substrate's user-facing outputs and decide placement for each. Silence is not an option." Then lists five outputs with an "or admin-only" alternative each.
The new standing rule from the prior round says: "every forced choice in this spec includes the criteria the implementer uses to pick." But the five substrate-output placements are forced choices without criteria. The executor must decide for each whether it goes to analyst journey or admin-only, but no criterion tells them which factor decides.
The spec gets the principle right at the top level (step 3, step 6) and forgets to apply it recursively to the new sub-choices it just introduced.
Severity: medium. The executor will pick something for each, and the picks will be defensible, but they won't be principled.
Fix: add to step 1 — "Criterion for placement of each substrate output: does a non-admin user (operator or analyst) need this information to do their job? If yes, the output surfaces in their journey. If the information is purely diagnostic for engineers debugging the substrate itself, it stays admin-only. The default for ambiguous cases is admin-only — surfacing engine internals has a cost, and substrate outputs with unproven decision-supporting value are better deferred than introduced and walked back."
Three sentences, applies the standing rule recursively, prevents implementer guessing.
RT-77. The coordination flag for substrate endpoints in step 3 path (a) creates an unresolved dependency cycle with #185.
Step 3 path (a) requires composing two substrate endpoints that don't exist by name yet: auto-annotations and conversion-rate-deltas. The Out of scope carve-out says "they would need to be added as part of step 3 if path (a) is picked, and the executor should confirm their existence (or plan their addition) before committing to path (a)."
This is honest, but it creates a problem: adding these endpoints is technically out of scope per the spec ("All other backend work, including new endpoints not listed above..."). So path (a) requires the executor to either:

(i) Add the endpoints as scope creep, in violation of "all other backend work" exclusion,
(ii) File a separate task to add them, then wait for that task to ship before continuing #199 (blocking dependency),
(iii) Pick path (b) instead.

The criterion in step 3 says pick (a) if the substrate is trustworthy. But the criterion for picking (a) is necessary, not sufficient — the substrate could be trustworthy AND the endpoints not exist, and (a) still wouldn't be feasible without separate scope.
Severity: medium. The executor will likely default to (b) when they hit this, because (a) has a hidden coordination cost the spec acknowledges but doesn't resolve.
Fix: clarify in step 3 — "Picking path (a) requires both: (i) the substrate is trustworthy per #185's behavioral verification, AND (ii) the two substrate endpoints (auto-annotations, conversion-rate-deltas) either already exist or can be added within this task's scope. If (ii) requires a separate task to add the endpoints, the executor must either (a) treat that as a blocking dependency and file the prerequisite task before proceeding with the Today step, OR (b) pick path (b) for #199 and create the substrate-driven follow-up that includes the endpoint-creation work as part of its scope."
This makes the implicit choice explicit: either accept the coordination cost or take the cheaper route. Both are defensible; defaulting via gravity isn't.

Fix (optional): add to step 7 — "Banner copy must include: a one-line acknowledgment that the navigation has changed, a link to the old → new mapping, and a dismiss button. Three elements, no more — the banner is informational, not a tutorial."
