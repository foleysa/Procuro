New findings against #268
F-101 — Severity rubric is referenced, not embedded [Major / Spec-defect]
Location: "Triage, score, and compute the decision" — "Classify every finding by severity ... per the v2 rubric." Step 1 says the v2 spec contains the rubric "table"; Step 6 just refers to "the rubric." But #268 itself does not contain the rubric text.
Why it matters: A task spec that defers its most consequential definitions to a yet-to-be-written sub-document creates a single-author bottleneck. The person writing v2 can write any rubric they want, including a permissive one, and still claim compliance with #268.
Fix: Embed the rubric verbatim in #268 (the §4 Edit 2 table from my review). The v2 spec then transcribes, it does not originate. Removes one degree of freedom from the bias surface.
F-102 — Hardened audit-log assertion: dropped from #268 [Major / Spec-defect]
Location: Search #268 for "before_state_hash" / "correlation_id" / "actor_ip" / "monotonically non-decreasing" — none present. The deliverables list mentions "before/after state hashes where applicable" and "correlation ID." That's it.
Why it matters: My review's F-007 was a replacement paragraph — the full enumeration of NIST SP 800-53 AU-3/AU-9/AU-10 fields plus the immutability test (PATCH/DELETE returns 403, attempts themselves audited). #268 reduced it to two phrases in a defect-template list. A tester reading #268 would not know to test audit-log immutability at all.
Fix: Add the full assertion text from §4 Edit 7 of my review to #268 as the audit-log line in Step 4 (Execute), not just to the defect template.
F-103 — "Risk-Accepted: <reason>" loophole [Major / Process-defect]
Location: Step 2 — "For any question that cannot be answered now, mark it 'Risk-Accepted: <reason>'."
Why it matters: This is the bias trap I flagged in my review (Axis 13 — "go-by-default unless..."). The 25 questions exist precisely because they're hard and uncomfortable. "Risk-Accepted" with a freeform reason field permits 25/25 questions to be deferred with reasons like "no second tenant available — accepted" and the run proceeds. The structural integrity of the gate depends on these being answered, not acknowledged.
Fix: Constrain the loophole. Three changes:

Cap Risk-Accepted to ≤5 of the 25 questions; >5 = the gate cannot be run, escalate.
Require sign-off on every Risk-Accepted by the exec sponsor (not the tester, not the reviewer) — by name, in writing, before kickoff.
Hard-list the questions that cannot be Risk-Accepted under any circumstance: Q4 (go/no-go rule), Q5 (severity rubric), Q9 (second tenant), Q10 (LLM model+version), Q13 (audit-log immutability), Q22 (prior security scan scope/findings), Q23 (rollback plan). Without these, the gate has no semantic content.

F-104 — Step 4 collapses 8 distinct security tests into one sentence [Blocker / Spec-defect]
Location: Step 4 — "one negative-test sweep covering CSV/Formula injection, XSS in supplier name rendered into HTML and PDF, SQL injection in supplier search, CSRF on an admin POST, JWT tenant_id tampering, login brute-force lockout, and a concurrent double-approve race."
Why it matters: This is exactly the failure pattern I called out in #263. Each item is a discrete test with discrete payloads, observable behaviors, and pass criteria. Collapsed into a "sweep," it becomes a checkbox a tester can score Pass after spending 10 minutes per item. The original #263 said "verify the funnel updates" — one sentence — and I rewrote it to a Given/When/Then. #268 just did the same compression eight times.
Fix: Each of the 8 items gets its own Given/When/Then in v2. Concrete payloads, concrete assertions. Estimate: 8 × ~150 words = ~1,200 words. Half a day to write. Catches 80% of the security failures the design partner's CISO would find.
F-105 — Step 4 also collapses i18n + L10N + perf-load into one sentence [Major / Spec-defect]
Location: Step 4 — "minimum sentinel tests in each previously-excluded category ... one mobile pass (iPad + iPhone smoke), one 1M-row CSV, the cross-tenant isolation step, the LLM-output integrity step ... one negative-test sweep ... and a concurrent double-approve race."
Why it matters: Same pattern as F-104. iPad smoke ≠ iPhone smoke (different OS, different screen, different gesture handlers). 1M-row CSV has multiple sub-tests (does it complete? does cancel work? does memory bound?). Each needs its own assertion.
Fix: Break Step 4 into Step 4a (Functional v2 spec end-to-end), Step 4b (Mobile sentinels — iPad and iPhone separately, named routes), Step 4c (Load sentinel — 1M-row CSV with named assertions), Step 4d (Cross-tenant), Step 4e (LLM output), Step 4f (Negative-test sweep with 8 sub-items per F-104), Step 4g (Race conditions).
F-106 — Tester independence: declared but not enforced [Major / Process-defect]
Location: Deliverables — "tester identity + independence declaration." Step 7 — "Produce ... independence declaration."
Why it matters: "Declaration" means "I assert I am independent." That's not a control. The original concern (my Axis 13) was that the implementer might be the tester; "I declare I am not the implementer" is self-attestation. Real independence requires structural separation: the tester is named before implementation began, or the tester comes from a different team, or the tester's compensation is uncoupled from the go decision.
Fix: Add to Step 2 (pre-flight) — "Tester is named in writing by the exec sponsor before the v2 spec is written. Tester has not committed code to api-server, command-center, or scripts/src in the trailing 30 days. If no such person is available, this is itself a Risk-Accepted answer to Q1 and counts toward the cap in F-103."
F-107 — "Independent reviewer" never defined [Major / Process-defect]
Location: Sign-off block — "tester, independent reviewer, exec sponsor."
Why it matters: Same problem as F-106 but worse. "Reviewer" appears in the sign-off chain with no role description, no independence criteria, no scope. A reviewer who reads only the report (not the evidence) provides a signature but no review.
Fix: Define reviewer scope explicitly: "Reviewer reads the full report, opens ≥3 random evidence directories, replays ≥1 step from the HAR, and confirms the computed go/no-go matches the defect log. Reviewer signs only after this. Reviewer must not be the tester or the implementer of any step under test."
F-108 — Pass-rate denominator gameable [Major / Spec-defect]
Location: Step 6 — "pass rate <95% of in-scope steps."
Why it matters: "In-scope" is the gameable variable. If a step fails, marking it Blocked-Environmental removes it from the denominator and lifts the pass rate. My review (F-021, F-046) defined the classes but not how they affect the rate. #268 inherits the ambiguity.
Fix: Pass rate denominator = (Pass + Fail + Blocked). Excluded only: Blocked-Environmental (third-party API down at run time, with timestamped evidence), N/A (step does not apply with stated reason). Blocked-Upstream counts as Fail for pass-rate purposes, because the upstream defect itself is the problem. State this in #268.
F-109 — Step 5 cleanup is itself untested [Minor / Spec-defect]
Location: Step 5 — "Execute the new Step 13 cleanup ... Record the cleanup itself as an audited admin action."
Why it matters: My review F-001 fix included "Is cleanup itself tested (i.e., 'broken cleanup script' found in UAT)?" — #268 records the cleanup in the audit log but does not assert correctness of the cleanup. If the cleanup script silently fails to mark one job acknowledged, the run still passes (because no one re-checks). Cleanup is the last step that runs; it has no follow-on test.
Fix: Add to Step 5 — "After cleanup completes, an independent re-check (different session, different correlation ID, ideally different tester) re-fetches /operations and /system and re-asserts the green criteria. Any discrepancy between cleanup-completion state and re-check state is itself a Blocker."
F-110 — Performance baselines have no thresholds [Major / Spec-defect]
Location: Step 7 — "performance baselines (page load, CSV ingest throughput, defense-pack generation time)."
Why it matters: "Baseline" is a measurement, not a gate. A 47-second defense-pack generation gets recorded as baseline=47s and the run passes. The customer experiences the 47s in pilot and complains. My review missed this; #268 inherited the miss.
Fix: Define thresholds. Suggested defaults (calibrate to your real targets):

Page load p95 ≤ 2.0s for /today, /opportunities, /fusion
CSV ingest throughput ≥ 10,000 rows/min steady state
Defense-pack generation p95 ≤ 30s for a typical opportunity
Any violation = Major. Embed as Given/When/Then in v2 spec.

F-111 — No "design-partner data shape" assertion [Major / Spec-defect]
Location: Q20 ("design partner's actual ICP/size profile") is in the questions list but the spec does not require seed data to match the answer.
Why it matters: The design partner is a real company with real data shape. If their procurement spend has 47,000 suppliers and the seed has 800, the entire UAT validates the wrong scale. My review F-030 added seed variants but did not require alignment to the specific design partner.
Fix: Add to Step 3 (environment prep) — "Seed scale parameters are validated against the design partner's intake survey numbers (supplier count ±20%, contract count ±20%, monthly invoice volume ±25%). If intake survey is unavailable, the run is performed at the largest scale variant and the smallest realistic variant; the report flags the alignment risk to the exec sponsor."
F-112 — No requirement to capture design-partner-specific feature flags [Minor / Spec-defect]
Location: Q19 lists feature flags but #268 does not require the pilot feature-flag set to be reproduced in UAT.
Why it matters: A UAT with feature-flags-as-of-dev-trunk passes; pilot flips a flag the design partner contracted for; the new code path was never tested.
Fix: Step 3 — "Feature flags during UAT match the documented pilot flag set for this specific design partner. Diff between UAT flags and pilot flags is captured in environment.json and any non-empty diff is a Blocker."
F-113 — Sign-off block has no rejection path [Minor / Process-defect]
Location: Step 7 — "obtain sign-offs."
Why it matters: What happens if a signer refuses? The spec is silent. Refusal is the most important thing a signature can express; an unsignable report has no protocol.
Fix: Add — "Any signer may refuse. A refusal is captured in writing in the report under §Sign-off with reason. Refusal by the reviewer or exec sponsor converts the computed result to No-Go regardless of the metric. Refusal by the tester triggers escalation to the exec sponsor; the sponsor may either order a re-run with a different tester or accept the refusal as No-Go."
F-114 — "Acknowledges (does not approve)" is a legal hedge that creates ambiguity [Minor / Process-defect]
Location: Step 7 — "the design-partner exec sponsor acknowledges (does not approve) the report before pilot kickoff."
Why it matters: I recommended this language in my review and I'm now red-teaming my own recommendation. Honest assessment: "acknowledge" is legally cute but operationally ambiguous. What does the design partner do with the report? Read it? Sign it? File it? If their CISO finds a Blocker after acknowledge, what's the remedy?
Fix: Replace with operational language — "The design partner receives the full report (not summary) ≥3 business days before pilot kickoff. The design partner's named technical reviewer signs an acknowledgment of receipt and confirms no objections to the documented residual risks. If they raise an objection, pilot kickoff is delayed pending resolution."
F-115 — Follow-up tasks: no SLA [Minor / Process-defect]
Location: Step 8 — "draft a one-line follow-up task description."
Why it matters: A Blocker filed and never planned is a Blocker the customer hits. My review F-002 made open Blockers a No-Go at gate time, but #268 has no rule for Blockers found after the gate (e.g., during pilot).
Fix: Add — "Any Blocker discovered post-go (during pilot) auto-converts the original Go to a retroactive No-Go for reporting purposes; the next UAT run must close it. Any Major discovered post-go is logged against the next UAT run's quality bar."
Defects my review missed that #268 also missed
Honest section. Things I should have caught in #263 and #268 inherited:
F-116 — No requirement to test the previous version [Major]
UAT tests the v2 build. But the design partner may already have data created on a prior build. Migration path / backward compatibility is untested. A real customer's onboarding is "import existing state"; UAT seeds from blank.
Fix: Add a step — "Seed Tenant C from a v(n-1) snapshot, run the migration, then run a subset of Steps 5–8 against it. Any divergence in defense-pack content, audit-log format, or opportunity classification between v(n-1)-migrated and v(n)-fresh = Blocker."
F-117 — No "first 5 minutes" test [Major]
A design partner's first impression is the first 5 minutes after login. The spec tests journeys, not impressions. No requirement that the first 5 minutes contain zero loading spinners >2s, zero empty states, zero "(coming soon)" labels, zero placeholder copy.
Fix: Add a Step 4h — "First-5-minutes test: as a brand-new tenant, time-box 5 minutes from login, screenshot every spinner >2s, every empty state, every placeholder. Each = Major (UX) for design-partner kickoff."
F-118 — No requirement that the spec author reads the report [Minor]
The spec author writes the v2 spec, then disappears. The tester writes the report. If the report shows the spec was unimplementable (e.g., a Given/When/Then that no real screen supports), the spec author should know. #268 has no feedback loop.
Fix: Add to Step 8 — "Spec author reads the final report and writes a 1-page 'spec lessons learned' note for the v3 spec. This is the only feedback loop preventing v3 from repeating v2's flaws."
F-119 — No abandonment criteria [Major]
Most consequential miss. If the run discovers, on day 1, that the platform is fundamentally unready (e.g., tenant isolation broken at API layer), is the tester required to complete all 13 steps? #268 implies yes (it's a checklist). Real testing organizations have an "abandonment" rule: if N Blockers discovered in first M% of run, halt and reset.
Fix: Add — "If ≥3 Blockers are discovered in the first 30% of step execution (Steps 1–4 of 13), the tester pauses and the triage owner decides whether to abandon the run. Abandonment = automatic No-Go and a hard reset back to spec revision. This prevents the 'sunk cost' bias of finishing a run that already cannot pass."
