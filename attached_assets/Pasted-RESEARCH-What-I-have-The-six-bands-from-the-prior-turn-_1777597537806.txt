THINK:
The mapping table needs to support three queries the platform will run constantly:

Signal-to-lever routing. "A signal arrived tagged with category X. Which levers should consume it?" Answer: find the bands category X belongs to, find the levers in those bands.
Lever-to-category applicability. "Lever Y is being scheduled for cycle. Which categories should it actually run on?" Answer: find the bands lever Y belongs to, find the categories in those bands.
Calibration-driven tier assignment. "For category X in band Z, what's the realization-vs-projection track record? Should this combination be Tier A, B, C?" Answer: query funnel calibration data filtered by category and band.

The schema needs to support all three without forcing N+1 queries.
Two table options:
Option A — Two many-to-many tables.

category_bands (category_code, band)
lever_bands (lever_id, band)

Routing queries become joins through the band column. Clean, normalized, easy to extend.
Option B — One denormalized mapping table.

category_lever_mappings (category_code, band, lever_id, attribution_tier, confidence_weight)

Materialized join. Faster reads, but inserts are explosive (every category × every applicable lever × every band combination is a row) and maintenance is harder when a lever joins or leaves a band.
Recommendation: Option A for canonical truth, with a denormalized view (v_category_lever_mappings) for the routing-hot-path. Best of both — normalization for maintenance, denormalization for query performance. Refresh the view when the truth tables change.
Going with Option A.

Schema

typescript// Truth table 1: which bands a category belongs to
export const categoryBands = pgTable('category_bands', {
  id: uuid('id').defaultRandom().primaryKey(),
  categoryCode: varchar('category_code', { length: 64 }).notNull(),
  band: bandEnum('band').notNull(),
  // Confidence in this mapping, calibrated over time from realization data.
  // Defaults to 1.0; updated by a periodic job that consumes funnel_snapshots
  // prior_calibration data per category-band combination.
  confidenceWeight: real('confidence_weight').default(1.0).notNull(),
  // Where the mapping came from. 'seed' for initial taxonomy, 'learned' for
  // mappings the calibration job adjusted, 'manual' for operator overrides.
  source: mappingSourceEnum('source').default('seed').notNull(),
  createdAt: timestamp('created_at').defaultNow().notNull(),
  updatedAt: timestamp('updated_at').defaultNow().notNull(),
}, (t) => ({
  categoryBandUnique: uniqueIndex('category_bands_unique').on(t.categoryCode, t.band),
  categoryIdx: index('category_bands_category_idx').on(t.categoryCode),
  bandIdx: index('category_bands_band_idx').on(t.band),
}));

// Truth table 2: which bands a lever belongs to
export const leverBands = pgTable('lever_bands', {
  id: uuid('id').defaultRandom().primaryKey(),
  leverId: varchar('lever_id', { length: 64 }).notNull(),
  band: bandEnum('band').notNull(),
  // Whether this lever is the primary fit for the band, or a secondary lever
  // that fires when the primary is excluded. Used for ranking inside a band.
  fitRank: integer('fit_rank').default(1).notNull(),
  createdAt: timestamp('created_at').defaultNow().notNull(),
}, (t) => ({
  leverBandUnique: uniqueIndex('lever_bands_unique').on(t.leverId, t.band),
  leverIdx: index('lever_bands_lever_idx').on(t.leverId),
  bandIdx: index('lever_bands_band_idx').on(t.band),
}));

// Enums
export const bandEnum = pgEnum('band', [
  'indexable',
  'concentrated',
  'fragmented',
  'subscription',
  'capital',
  'services',
]);

export const mappingSourceEnum = pgEnum('mapping_source', [
  'seed',
  'learned',
  'manual',
]);

// Denormalized view, refreshed by a job when the truth tables change.
// Materializes the join for the routing hot path.
export const categoryLeverMappings = pgMaterializedView('v_category_lever_mappings').as(
  (qb) => qb
    .select({
      categoryCode: categoryBands.categoryCode,
      band: categoryBands.band,
      leverId: leverBands.leverId,
      categoryConfidence: categoryBands.confidenceWeight,
      leverFitRank: leverBands.fitRank,
    })
    .from(categoryBands)
    .innerJoin(leverBands, eq(categoryBands.band, leverBands.band))
);
The materialized view refreshes on insert/update/delete to either truth table (trigger-based) or on a schedule (every cycle's prep step). Trigger-based is cleaner; schedule-based is safer if the trigger overhead becomes a concern.

Routing queries
Three queries the platform will run constantly. Using the materialized view:
Signal-to-lever routing:
sqlSELECT DISTINCT lever_id, MIN(lever_fit_rank) as best_fit
FROM v_category_lever_mappings
WHERE category_code = $1
GROUP BY lever_id
ORDER BY best_fit ASC;
Lever-to-category applicability:
sqlSELECT DISTINCT category_code, MAX(category_confidence) as best_confidence
FROM v_category_lever_mappings
WHERE lever_id = $1
GROUP BY category_code
ORDER BY best_confidence DESC;
Tier assignment query (joins to funnel calibration):
sqlSELECT 
  m.category_code,
  m.band,
  m.lever_id,
  c.realization_count,
  c.delta_median_abs_error,
  CASE
    WHEN c.realization_count < 10 THEN 'insufficient_data'
    WHEN c.delta_median_abs_error < -100 THEN 'tier_a'
    WHEN c.delta_median_abs_error BETWEEN -100 AND 100 THEN 'tier_b'
    ELSE 'tier_c_or_d'
  END as suggested_tier
FROM v_category_lever_mappings m
LEFT JOIN funnel_prior_calibration c 
  ON c.lever_id = m.lever_id 
  AND c.category_code = m.category_code 
  AND c.window_days = 90;
The tier suggestion uses the prior calibration math from #185 (median absolute error, n≥10 gating, $100 dead-band).
