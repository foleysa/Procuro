PART 1 — ALERTS MIGRATION (#117)

Current live DB schema for alerts:
   body, ref_type, ref_id, metadata, resolved_at

Declared schema (target state):
   state, source, payload, acknowledgedAt, snoozedUntil

Steps:
1.1  Generate the Drizzle migration that transforms live → declared. Use 
     `pnpm drizzle-kit generate` from the lib/db package. Inspect the SQL it 
     produces. Do not run it yet.

1.2  Review the generated SQL by hand. Confirm:
     - It renames or migrates data from old columns to new where semantics map 
       (body → payload, ref_type/ref_id → source, resolved_at → acknowledgedAt 
       or similar — verify against the schema file's intent)
     - It preserves existing alert rows; this is not a drop-and-recreate
     - It handles NULLs and any constraints correctly

1.3  Apply the migration to a local/dev DB first. Verify with a few sample 
     queries that existing alert rows survived and have sensible values in the 
     new columns.

1.4  Apply to the live DB. Confirm with: SELECT column_name FROM 
     information_schema.columns WHERE table_name = 'alerts'; and check the new 
     columns are present.

1.5  Remove the workaround in the Today aggregator. Find the alerts sub-query 
     that filters on resolvedAt IS NULL and groups by severity (the #209 patch). 
     Replace it with the proper query that uses the new schema (filter on state, 
     group by source/severity per the original #117 design). Verify the Today 
     page still loads.

1.6  Audit every other call site that touches the alerts table. Use grep:
     grep -r "alerts\." --include="*.ts" .
     grep -r "from.*alerts" --include="*.ts" .
     For each hit, confirm it now compiles and runs against the new schema. 
     Re-enable any code that was commented out or stubbed because of the drift.

1.7  Run the test suite. If any alerts-related tests exist, they should now 
     pass. Add a new test that confirms the alerts table has the expected 
     columns (a schema-introspection test).
