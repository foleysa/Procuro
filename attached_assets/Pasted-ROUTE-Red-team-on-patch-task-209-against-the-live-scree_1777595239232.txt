MEDIUM — completeness of the three proposed fixes
RT-84. The "no raw SQL in DOM" contract is correctly scoped at the failed-source level but doesn't account for partial failures within a successful response.
The spec says: "Today page never displays a raw SQL error string, query parameters, or stack-trace text. When a source is unavailable, the card shows a short, plain-language message."
But the aggregator's discriminated-union response (from #199) has both a partial: boolean flag and per-source errors: Array<{source, error}>. The patch covers the case where the source is in errors (failed). It doesn't cover the case where a source returns a successful response that contains an error string — e.g., if alerts returns {state: "error", message: "Failed query: select ..."} instead of throwing. The current screenshot is exactly this case: the page shows "No alerts data" AND a raw SQL string, suggesting the alerts source is partially returning data alongside the error rather than throwing cleanly.
Severity: medium. The fix as written likely covers the screenshot's specific case (the SQL is in the failure state), but the contract should be broader.
Fix: rephrase the contract — "The Today page never displays raw SQL, query parameters, stack-trace text, file paths, or function names anywhere in any rendered card or banner, regardless of whether the underlying source returned a 5xx, returned 200 with an error payload, or returned 200 with malformed data. The contract is enforced via a render-time scrubber that strips known patterns (SQL keywords like 'select/from/where', dollar-prefixed param markers, stack-trace artifacts) from any user-facing error text. The disclosure component is the only place these patterns are allowed."
RT-85. The "What happened?" disclosure has no activation rule.
Step 1 says "engineers can click a What happened? disclosure to see the technical detail." But what shows the disclosure? Is it always visible? Role-gated? Dev-mode-only? Hidden behind a feature flag? An admin-only sidebar?
If always visible, every user sees an inviting "What happened?" link on every error and clicks it expecting a friendly answer, getting a SQL stack trace.
If role-gated to admin/engineer roles, the spec should say so.
If dev-mode-only, the spec should say what activates dev mode.
Severity: medium. The executor will pick something, and the pick will be either wrong (visible to all) or right (gated) but undocumented.
Fix: specify activation. Recommend: "The disclosure is visible only to users with the operator/admin role. For non-operator users, the card shows the plain-language message with no disclosure affordance. This matches the role-gated nav rendering pattern from #199 step 2."
RT-86. Deep-link query strings aren't enumerated for the four cards.
Step 5 says "Deep-link the four card 'Open →' links to the right filtered slice of each destination page. Reuse existing query-param conventions where they exist; add minimal new ones only where needed."
What do the destination pages support today? "Reuse existing conventions" assumes conventions exist. If they're inconsistent across pages (e.g., Alerts uses ?status=open while Approvals uses ?filter=pending), this becomes an executor-discovery rabbit hole.
Severity: medium. The work happens, but the executor invents conventions where they don't exist and the result is inconsistent.
Fix: require the executor to enumerate existing conventions in the four destination pages first, then state in the design doc which conventions are reused vs. added. If new conventions are added, they follow a consistent pattern (recommend ?filter=key:value pairs for consistency).

Pattern observation worth noting in next /pattern review:
This is the first patch task in the spec-iteration arc that started with #185 and continued through #199. Patch tasks have a different shape than foundational specs — they're tactical, surgical, and time-pressure-driven (the Today page is broken now, the operator sees a SQL leak now). The standing rules still apply, but the failure mode is different: foundational specs fail by being too vague at the architecture level; patch specs fail by being too narrow at the structural level. The same rule that catches "this spec doesn't define how to pick" in a foundational context catches "this patch doesn't ask whether it should still ship" in a patch context.
Worth noting that the patch-task failure mode (RT-82 — patching a stopgap without checking whether the trigger to retire it has fired) is the natural counterpart to the foundational-task failure mode (forced choices without criteria). The rule is the same — "decisions need criteria, including the decision to do this work at all" — but its application differs by task type. Worth elevating in the next /pattern review whether to formalize this as a sub-rule: "patch tasks must check whether the conditions that produced the original stopgap have changed."
