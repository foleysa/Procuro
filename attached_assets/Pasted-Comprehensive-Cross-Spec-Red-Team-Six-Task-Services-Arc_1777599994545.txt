PART 2: NEW CROSS-SPEC INTEGRATION FINDINGS
These are issues that emerge only when you look at the six specs as a system.
RT-145 (CRITICAL): Task #216 inherits #215's broken wage-vs-rate assumption AND amplifies it.
Task #216 Step 2 (services_rate_card_benchmark analyzer) says: "join rate_card_lines to OEWS wage_benchmark signals on (roleTitle → SOC mapping, region → OEWS area code)... compute the percentile rank of the rate card rate against OEWS percentiles. If the rate is at or above the 90th percentile, emit an opportunity..."
This is the analyzer comparing tenant bill rates directly to OEWS wages with NO markup model. Per RT-133 in #215's prior round, this systematically generates false-positive recommendations (everything looks like 5x overpriced because bill rates ARE 1.5-3x wages by definition).
Combined finding: #215 ingests wages without flagging them as wages, and #216 consumes them as if they were bill rates. This is a two-spec compound failure that the individual reviews caught only partially — RT-133 said "Task #4 must apply markup," but Task #216 (which IS Task #4 in the arc) doesn't apply markup. The two specs disagree about whose responsibility the markup is, and neither addresses it.
Severity: critical. This is the failure mode F500 customers will see on day one of the services pass.
Fix: the markup model needs an explicit owner. Recommend it lives in #216 (closer to the analysis logic) but #215 must emit metadata indicating wage-not-rate. Task #216 step 2 must be updated to:

Apply a markup multiplier per supplier-tier or per role-category before percentile comparison.
The markup table is seeded with reasonable defaults (1.5x for staffing, 2x for IT services, 2.5x for consulting, 3x for Big-Four advisory).
The markup multiplier is configurable per tenant via admin UI (not in scope here, but referenced as future work).
Opportunities surface the markup assumption in their rationale so operators can challenge it.

RT-146 (CRITICAL): The cohortKey() contract has drift across specs.
#213 specifies cohortKey() as part of the lever interface. #218 references "leverId-categoryCode" composite keys for calibration but doesn't reconcile with cohortKey().
#216 has each lever defining its own cohortKey():

services_rate_card_benchmark: (supplierId, rateCardLineId)
scope_management: (supplierId, sowId)
hours_audit: (supplierId, sowId, personIdentifier?)
sow_to_msa_conversion: (supplierId)

But #218's calibration keying is <leverId>:<categoryCode>. The categoryCode dimension isn't in any of #216's cohortKeys. So how does an opportunity from services_rate_card_benchmark get assigned a categoryCode for #218's bucketing?
The answer must be: the opportunity row carries categoryId (referencing categoriesTable) and #218 resolves it via opportunities.categoryId → categories.code. Specs don't make this explicit.
But there's a deeper issue: a single SOW might have multiple rate card lines covering DIFFERENT categories (a consulting SOW might use both PROF_CONSULTING_STRATEGY and PROF_LEGAL roles). cohortKey for services_rate_card_benchmark is (supplierId, rateCardLineId) — but rateCardLine doesn't carry a category. The opportunity's category assignment is ambiguous in this case.
Severity: critical. Calibration accuracy depends on consistent category assignment to opportunities; the spec arc doesn't define how that happens for services-side opportunities that span categories.
Fix: add to #216: every opportunity an analyzer emits MUST set opportunity.categoryId based on a deterministic rule. For services_rate_card_benchmark, the categoryId comes from the role-to-category mapping (e.g., a "Senior Consultant" role mapped to PROF_CONSULTING_STRATEGY). For scope_management/hours_audit, the categoryId comes from the SOW's parent contract's category. For sow_to_msa_conversion, the categoryId comes from the dominant category among the supplier's SOWs. State this explicitly so #218's bucketing is well-defined.
RT-147 (HIGH): Schema co-evolution conflict on opportunities table.
Multiple specs add columns to opportunities:

#213: mappedVia (text/varchar)
#213 (per absorbed RT-108): re_categorized_after_persistence (boolean)
#216: categoryId (referenced but presumably already exists)
Implicit from #218: categoryId must be populated by all analyzers

What's the migration order? #213 adds mappedVia first. Then any spec ordering. But if #213 ships and #216 ships before #218, opportunities created during that window have categoryId set by analyzers but no calibration bucketing exists yet. When #218 ships, it bucket-keys retroactively — but per its own spec, "Re-running calibration retroactively against old funnel snapshots — going-forward cycles compute the new per-(category, lever) metric; old snapshots stay per-lever-only."
So opportunities created in the gap between #216 ship and #218 ship contribute to per-lever calibration but never to per-(category, lever) calibration. That's not data corruption per se, but it means the per-(category, lever) metric has a "no data for this combination" period for several weeks even after #218 ships, depending on cycle frequency.
Severity: high. Not data corruption but a timing-dependent gap that affects #218's value.
Fix: the spec arc needs a sequencing note. Recommend: ship #213 first (foundation). Then ship #218 BEFORE #216 (so per-(category, lever) bucketing exists when services analyzers start emitting). Then ship #214 + #215 (data + signals). Then ship #216 (analyzers). Then ship #217 (UX). Or alternatively, ship #218 alongside or after #216 but accept the calibration gap and document it.
RT-148 (HIGH): The services taxonomy and the bands seed have a chicken-and-egg dependency that's not explicit.
#213 step 5 says: "Seed category_bands for canonical category codes (existing CANONICAL_CATEGORY_CODES — freight/logistics) — Indexable + Concentrated dual assignment per the doc's Layer-1 table." It also says: "Note: services-side categories (Professional Services, HR/Contingent, Marketing, Telecom, etc.) are seeded by Task #2 — leave them out here."
#214 step 8 says: "Add to lib/db/seeds/taxonomy.sql (the seed file from Task #1): All Professional Services, HR, Engineering codes → Services band primary, Concentrated band secondary..."
So #213's seed file is INCOMPLETE on day 1 (it doesn't cover services categories). When #214 ships, it adds rows to that seed file. But what happens between ship dates?
If a customer onboards between #213 ship and #214 ship, and that customer tags spend with what would be services categories, those categories have no canonical code (because #213 didn't add them) and no band (because #214 hasn't shipped). The customer's services spend flows through Layer B (Fragmented fallback) entirely.
When #214 ships, the services categories get canonical codes and band assignments. But existing opportunities tagged with mapped_via='unmapped_default' aren't retroactively re-routed (per #213's own retroactive semantics).
So: customers who onboard between #213 and #214 ship dates have permanent services-side data tagged incorrectly. There's no migration to fix this.
Severity: high. Not data corruption but produces a long-tail data-quality issue.
Fix: either (a) ship #213 and #214 atomically (same release), or (b) add a one-time "re-route post-#214-launch" migration that re-tags opportunities whose tenant-string source matches a synonym now in the registry. The latter contradicts #213's "going-forward only" rule, so it would need explicit framing as a one-time exception. Recommend (a).
RT-149 (HIGH): The data model for services entities (#214) has inconsistencies with what the lever analyzers (#216) need.
Walking through what #216 actually requires vs. what #214 provides:
#216 services_rate_card_benchmark needs:

rate_card_lines.roleTitle → mapped to SOC code (lookup table)
rate_card_lines.region → matched to OEWS area code
rate_card_lines.rateAmount → compared to OEWS percentile

The region field in #214's rate_card_lines is "text — e.g., US-Onshore, Nearshore-LATAM, Offshore-India". But OEWS area codes are FIPS-derived (state codes, MSA codes). There's no mapping defined between "US-Onshore" (which could be any of the 50 states) and a specific OEWS area code.
This means #216's analyzer can't actually join on region in any meaningful way unless either (a) the rate card region is normalized to OEWS-compatible codes or (b) a mapping table is built.
Severity: high. The lever as specified can't function with the data as specified.
Fix: #214 needs a region normalization step. Either (a) standardize rate card region codes to OEWS area codes (FIPS-style), or (b) add a region_mapping table that maps tenant-friendly region names ("US-Onshore") to OEWS area code lists. Recommend (b) — preserves tenant-friendly UX while enabling join.
RT-150 (HIGH): Time entries' personIdentifier field has cascading uses that compound the privacy risk.
Per RT-115 (still unaddressed), personIdentifier is a privacy hazard. But across the arc:

#214 stores it in time_entries.
#216's hours_audit analyzer uses it: "if any individual personIdentifier is billing > 60h/week sustained over 4+ weeks (overload → rework risk)... emit a separate opportunity with that person's pattern."
#217's supplier 360 surface uses it: "Utilization signals (count of person-identifiers with overload or under-util flags from the hours-audit analyzer)."

So personIdentifier flows from ingest → analyzer → opportunity → UI surface. The privacy exposure isn't just storage; it's that the platform displays per-person information in the supplier 360 page. F500 procurement orgs explicitly avoid this — they look at role-level utilization, not person-level — for legal exposure reasons.
Severity: critical. The privacy hazard isn't just data-at-rest; it's data-in-use across three specs.
Fix: combined with RT-115's fix — drop personIdentifier in favor of role+supplier+region aggregation. Update #216 hours_audit to detect role-level utilization patterns (e.g., "the Senior Consultant role at this supplier showed sustained 60+ hour weeks across multiple consultants over 4 weeks"). Update #217's supplier 360 to show role-level patterns, not person-level. This requires changes across all three specs.
RT-151 (MEDIUM): #218's tier suggestion classification thresholds may be miscalibrated for services.
#218 step 4 states the tier classification:

improvementUsd > +100 → tier_a
improvementUsd between -100 and +100 → tier_b
improvementUsd < -100 → tier_c_or_d

This mirrors #185's per-lever calibration thresholds. But services-side opportunities have different magnitude characteristics from materials:

Materials opportunities: typical realized savings $10K-$500K per opportunity (rebid wins, hedge gains).
Services opportunities: rate-card-benchmark might realize $50K-$200K (rate negotiation), but scope_management on a $5M SOW with 15% over-run is a $750K opportunity.

A $100 dead-band is meaningful for materials (where typical realizations are 5-7 figures). For services, where the variance is wider, $100 is rounding error. The dead-band should scale with median realization size, or be lever-specific.
Severity: medium. The metric will fire correctly but the dead-band may produce more "neutral" verdicts than is useful for services levers.
Fix: add to #218: dead-band thresholds are configurable per-lever. Default $100 for materials levers; default $1,000 for services levers. Document the rationale.
RT-152 (MEDIUM): The Services nav placement is unresolved across #213 and #217.
#213's UI section says: "/admin/taxonomy/queue in the Engine section."
#217 step 3 says: "Services nav section. Add a 'Services' entry in the existing nav (place per #199's IA — likely under Operations as a sibling of Suppliers/Contracts, or under Engine if the IA puts it there)."
Per the prior #199 red-team round (RT-69), the friendlier-path naming for the funnel substrate's section was supposed to be committed in the design doc. But the specs both punt: #213 says "Engine section" without committing the path, #217 says "Operations or Engine" with explicit ambiguity.
Severity: medium. Will be resolved at implementation but creates inconsistency risk.
Fix: before any of these specs ship, the #199 IA design doc must be re-checked or finalized to commit Engine vs Operations placement. All three specs (#213, #217, #218) reference admin-funnel surfaces; they should all live under the same section.
RT-153 (MEDIUM): The OEWS data lag (~11 months) compounds across specs.
#215 has OEWS data lag (RT-138 from prior round, status: NOT ABSORBED).
#216 consumes OEWS in services_rate_card_benchmark.
#217 surfaces OEWS-derived color-coding on rate-card detail.
#218 may include rate-card-benchmark calibration in tier suggestions.
Each downstream consumer makes the staleness less visible. By the time a user sees a red cell on a rate card detail page (#217), the underlying benchmark might be 18+ months stale, but the UI just shows "red" without indicating staleness.
Severity: medium.
Fix: add to all three specs (#215 emit, #216 analyze, #217 display) a data_age_months field that surfaces the staleness through to the UI. The rate card cell should show "red (data 14 months old)" rather than just "red."
RT-154 (MEDIUM): #218's per-(category, lever) bucketing has a sparse-data problem services will hit hard.
For per-(category, lever) bucketing to produce meaningful tier suggestions, each combination needs n ≥ 10 realized opportunities. With the cohort identity rules from prior rounds:

A tenant with 5 SOWs across 3 categories generates 15 (sow, category) combinations but only realizes opportunities on a fraction of them.
The n ≥ 10 gate means most (category, lever) pairs will say "insufficient_data" for months or years.

Services opportunities are higher-stakes, lower-volume than materials. A tenant might realize 3 rate-card-benchmark opportunities a year. n=10 takes 3+ years of data per (category, lever) combination.
Severity: medium. Not wrong, but the per-(category, lever) tier metric will be mostly "insufficient_data" for services levers for years.
Fix: add to #218 architectural notes: "Services-side levers with low realization volume may take 1-3 years of data to populate per-(category, lever) calibration. The fellBackToLeverRollup mechanism is the primary signal for those levers in the medium term. Consider a sliding-window aggregation that pools across similar categories (e.g., all PROF_* codes share a calibration bucket) for low-volume levers."
RT-155 (LOW): The "by Band" lens on Spend Overview (#217) doesn't address legacy/unmapped categories cleanly.
#217 step 2 says: "When a category has no band (legacy / unmapped), it appears in the Fragmented band with a small 'unmapped' indicator (the routing-layer fallback from Task #1)."
But this conflates two different states:

Categories that exist but have no band assignment yet (operator hasn't curated them).
Categories that flow through Layer B (Fragmented fallback) for tenant-string matching.

Both end up in Fragmented with an "unmapped" indicator, but they're different problems with different fixes. A category with no band needs an admin to assign one. A tenant string with no synonym needs an admin to map it.
Severity: low. The UI conflation doesn't break anything but makes operator triage harder.
Fix: distinguish in #217: two indicators, "unmapped category" (no band assignment) vs. "unmapped tenant string" (Layer B fallback in flight). Each links to a different admin action.
RT-156 (LOW): The CSV templates for services entities (#214) don't address change-order workflow.
#214 step 10 lists CSV templates for: statements_of_work.csv, rate_cards.csv, rate_card_lines.csv, time_entries.csv. Missing: sow_milestones.csv, sow_change_orders.csv (both referenced as sub-tables in step 4).
Without templates for sub-tables, customers ingesting historical SOW data can't capture milestones or change orders via CSV. The scope_management analyzer needs change orders to fire properly.
Severity: low. Can be added in implementation.
Fix: add sow_milestones.csv and sow_change_orders.csv to #214's CSV template list.

PART 3: ARCHITECTURAL COHERENCE AND MISSING PIECES
RT-157 (HIGH): No spec addresses currency handling consistently.

#214 has currency on rate_cards (good), but notToExceedUsd/committedValueUsd/burnedValueUsd on SOW (assumes USD).
#215 OEWS wage data is in USD only.
#216 analyzers compare rates without currency conversion logic.
#217 displays values without currency conversion.

A tenant with a USD MSA, GBP SOW, and EUR-billed time entries would have analytics failures across the stack.
Severity: high. Multi-currency procurement is the F500 default, not the exception.
Fix: the arc needs a currency-handling spec — or each spec needs a currency-handling section. At minimum:

Every monetary field has an associated currency column.
A tenant base currency is configured.
All comparisons happen in tenant base currency with conversion at a documented rate (e.g., daily fixing).
The conversion logic lives in a shared utility (probably under intelligence/routing/ or its own module).

This is RT-123 from #214 prior round generalized across the arc.
RT-158 (HIGH): No spec addresses what happens when a services category has both Indexable AND Services band assignments.
The bands seed in #214 step 8 says: "FAC_LEASES → Concentrated + Services" and "FAC_UTILITIES → Indexable (energy) + Concentrated."
But what about categories with BOTH Indexable and Services band — e.g., MKT_AGENCY_CREATIVE could have both PCU index data (indexable lever applicability) AND rate-card data (services lever applicability)? The spec doesn't say it can have both, but it doesn't say it can't.
If a category has both bands, both Indexable levers AND Services levers fire on it. Multiple opportunities for the same spend get generated by different levers. The funnel calibration's per-(category, lever) bucketing handles this correctly per #218, but the operator UX might surface duplicate-looking recommendations.
Severity: high. Not data corruption but cohesion issue at the operator-experience level.
Fix: add to #213 architectural notes: "A category can have multiple band assignments (the schema allows it). When a category has both Indexable and Services bands, both lever sets fire and may generate concurrent opportunities. The opportunities are independent and shouldn't be merged automatically. The UI (#217) should group recommendations per-category showing all active levers, not per-lever showing all categories."
RT-159 (HIGH): The ingest-writer doesn't address validation failures across services entities.
#214 step 6: "Extend IngestPayload... Add the corresponding stages to the writer (after contracts; before POs since SOWs may reference contracts)."
But what if a SOW references a contractId that doesn't exist? Idempotency rules say upsert on (orgId, sourceSystem, sourceExternalId) — but this doesn't enforce the FK. What if a rate_card_line references a rateCardId that hasn't been created yet (out-of-order CSV)?
The spec doesn't describe validation behavior. The executor might:

(a) Fail the entire ingest if any FK is missing.
(b) Skip the offending row silently.
(c) Insert with NULL FK and queue for review.

Each has different operator implications.
Severity: high. Critical for ingest reliability with messy real-world data.
Fix: specify validation behavior. Recommend (c) — queue rejected rows in a new ingestion_failures table with the source row data, the reason, and an operator review action.
RT-160 (HIGH): No spec addresses tenant offboarding or data deletion for services entities.
The arc adds many new tables: synonym_registry, unmapped_category_queue, statements_of_work, sow_milestones, sow_change_orders, rate_cards, rate_card_lines, time_entries, plus new columns on opportunities, contracts, categories, market_signals.
When a tenant is hard-deleted (GDPR right to erasure, contract termination), all their data across all these tables needs to be removed. The cascade behavior isn't specified anywhere.
Severity: high for compliance. The platform's GDPR posture depends on cascading deletion working correctly.
Fix: add to the arc — a tenant-offboarding spec or a cross-cutting note in each of these specs ensuring foreign keys cascade on tenant deletion. Time-entries with personIdentifier especially needs explicit GDPR-compliant deletion.
RT-161 (MEDIUM): The arc has no spec for testing the integration of all six pieces.
Each spec has its own tests. None tests the full path: tenant uploads CSV → ingest → routing → cycle → analyzer → opportunity → calibration → tier suggestion → UI display.
Integration test gaps:

A tenant uploading a services CSV should produce the expected opportunities.
A category resolution from Layer B → Layer C → Layer A (through operator action) should re-route correctly.
A rate card with OEWS-mapped roles should generate rate-card-benchmark opportunities with correct currency handling.

Severity: medium.
Fix: add an integration test spec or include integration-test scope in each spec. Most natural is a "services E2E test" that spans #214-#216 with a representative tenant.
RT-162 (MEDIUM): No spec addresses the operator-onboarding workflow for the new admin surfaces.
The arc adds three new admin surfaces:

/admin/taxonomy/queue (#213)
Services nav with three tabs (#217)
Per-(category, lever) tier matrix on admin-funnel (#218)

Plus extends supplier-detail, contract-detail, spend.

Severity: medium. UX completeness, not architectural.

RT-163 (LOW): The arc doesn't address performance budgets for the new collectors/analyzers.

#215 adds OEWS collection (annual but heavy data per pull).

ARCHITECTURAL COHERENCE: WHAT BLOCKS THE ARC AS A SYSTEM
The six specs together build a competent services-side procurement intelligence stack. But three system-level issues need addressing before the arc ships:

Ship sequence discipline. The specs reference each other's data without a defined order. Without a sequence, deploys can land in orders that produce permanent data quality issues.
Currency handling as a cross-cutting concern. No spec owns multi-currency. Each spec assumes USD. The arc as a whole produces wrong analytics for any tenant with non-USD operations.
Tenant lifecycle (onboarding, offboarding). The arc adds many tables; none address what happens when a tenant is created or deleted. GDPR posture depends on getting this right.

These aren't bugs in any individual spec; they're gaps in the arc's design.
